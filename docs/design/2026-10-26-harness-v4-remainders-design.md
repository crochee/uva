# harness v4 遗留收口与基座承诺 — 设计

日期：2026-10-26
分支：`feature/harness-v4`（worktree `.worktrees/harness-v4`）
前序：[harness v4 设计](2026-10-26-harness-v4-design.md) / [验收记录](2026-10-26-harness-v4-acceptance.md)

## 1. 意图与为什么

harness v4 的重构本身已经做完并通过验收（依赖计数 0/0/0，`make ci` 全绿，场景 A–I 端到端通过）。
剩下的不是"harness 还不够好"，而是**它还不能被交出去**：

- 八项遗留里，有三项能让会话跑死或丢东西，有三项是"不报错但两边不一致"，一项是纯整理，
  一项是本分支之外的既有欠债。
- 更要紧的是：它现在的形态还**没有承诺**。公开面会随下一次改动漂，日志格式里的
  `schema_version` 写了但没有任何读端分支它（今天读到 v99 的日志和读到 v1 一样，区别只是不读），
  外部贡献者没有第一份材料。

本轮的目标是把 harness 从"重构完成"变成"可以当基座交出去"：修完遗留，落两条承诺
（公开 API 冻结、日志格式版本化），补交接面。

## 2. 目标

| # | 目标 | 怎么算达成 |
|---|---|---|
| G1 | 八项遗留全部修正 | 每项有一个**去掉修复就失败**的测试 |
| G2 | 日志格式的版本号变成真门禁 | 读到比自己新的 `schema_version` 必须拒绝，不许静默误读 |
| G3 | 公开 API 冻结 | 一份承诺清单 + 一条门禁，新增公开名会让门禁失败 |
| G4 | 交接面三件套 | 公开面清单、格式兼容说明、给外部贡献者的第一份材料 |
| G5 | `make test-crates` 全绿 | 四个 crate 的失败各自有根因修复；`make ci` 之后新增它为门禁 |
| G6 | 验收记录覆盖本轮 | 现有验收记录补上本轮的门禁与场景结果 |

## 3. 非目标

- **不新增能力。** 本轮不引入新工具、新协议字段、新 provider。
- **不给 harness 加 re-export。** `Spawner` / `ModelProvider` / `Tool` 不从 `elysper-harness` 转出 ——
  理由不是会加依赖（harness 本来就依赖 core/provider/tool），而是：被承诺的那张面应该是 harness 自己的面，而它零运行时的承诺不应该被别的 crate 的 feature 集绑住。改文档（见 G 项）。
- **不给旧会话日志做迁移。** 见 §5 的"我的决定"。
- **不冻结 server 的 HTTP 表面。** `/api/v1` 的 URL 本身就是版本；冻结清单只覆盖库 crate 的精选公开面。
- **不改插件协议的 wire。** `elysper-plugin-protocol` 的方法集与能力协商本轮不动。

## 4. 反目标（做到这些也仍然算失败）

- **A1 "绿"来自改门禁而不是改代码。** 门禁是判据，不是可调参数。（前例：验收时 `make ci` 因三个
  文档链接红 —— 修链接是对的，改门禁不是。）
- **A2 冻结清单只是一份当前 `pub use` 的快照。** 快照不是承诺。清单必须说清**哪些名字不会变**、
  **变了怎么办**，否则它只是一份会过期的清单。
- **A3 版本号仍然不门禁。** 今天 `schema_version` 就是装饰品；加了号还不用，等于没加。
- **A4 八项修成八个互不相干的补丁。** 分支会更大而不是更清楚。
- **A5 交接文档复述代码。** 新人要知道的是"从 clone 到跑通一条 turn 要做什么"。

## 5. 约束

来自仓库既有规范（`AGENTS.md`）与本分支已建立的基线：

- 库用 `thiserror`、应用用 `anyhow`；`max_width = 80`；禁通配符导入。
- `elysper-harness` 不得有 `[features]`，闭包内不得出现 tokio，库的公开面不得出现运行时类型
  （`make check-no-runtime` / `make check-harness-features` / `make check-public-api-runtime`）。
- harness 私有项的 `///` 预算**正好 50/50**（`make check-harness-docs`）—— 新增任何一行都要先删一行。
- 公开面已有的两条门禁是本轮冻结清单的落脚点：`make check-pub-surface`（禁 glob re-export）、
  `make check-pub-surface-strict`（逐 crate 的 `pub use` 计数基线）。
- `make check-test-layout`：内联测试块 < 400 行；新测试放同级 `tests.rs`。
- `make check-clock`：库生产代码不得直接 `chrono::Utc::now()`。
- `make check-claim-language`：状态文档里不许有与代码矛盾的绝对化措辞。
- TDD：先写失败的测试。提交信息用英文祈使句。逐 crate 跑测试，不跑 `cargo test --workspace`。
- 不推送远端。

### 我的决定（除非你反对，写进计划即生效）

1. **日志格式不做向后迁移。** crate 还在 0.1，老会话日志数量有限；迁移代码比"重开一个会话"更容易出新
   bug。本轮把"格式变了、老日志不保证"写在明处。版本号**现在就埋**（G2），所以以后再改格式有路可走。
2. **公开 API 冻结只覆盖库 crate 的精选面**（外部能写下的那些名字），**不覆盖深路径**。具体到
   `elysper-harness` 是那 **60 个** 精选名字；走深路径才够得着的另外 **64 个** `pub` 名
   **不在承诺内**，将来可动。不冻结 server 的 HTTP 面（`/api/v1` 的 URL 本身就是版本）。
3. **冻结清单的形态是"人可读的承诺 + 机器可读的门禁"两份**，不是一份。承诺写进文档并说明变更流程；
   门禁是脚本，失败信息直接指向"你新增了哪个公开名"。
4. **冻结基线在第一到第三波全部落地之后才计算。** C 与 E 会动公开面上的名字；先冻结再改，
   等于第一波就违约。
5. **G 是"把话说准"，不是新门禁。** 依赖数写进文档时必须与 `cargo tree` 的实际输出一致，但
   本轮不为它建门禁 —— 本轮建的唯一新门禁是 G3 的冻结门禁。再加一个必然漂移的门禁，是拿噪音
   换安全感。
6. **D 的三个码各自的客户端动作**（我定）：`stale_resume` 拆成"已应用"（幂等成功，不再报 409）、
   "日志已被推进"（409 + 明确冲突说明，客户端重新拉状态后再决定）、
   "没有快照"（409 + 明确说明这一轮不能续，建议重开会话）。每个码自带名字与理由，不共用一个
   `stale`。
7. **语言**：面向外部的东西用英文（crate README、贡献者第一份材料、格式兼容说明），
   面向内部的（设计、计划、验收记录）跟仓库现状用中文。

### 5.1 仓库已经定死的事实（不再问）

| 事实 | 出处 | 对计划的影响 |
|---|---|---|
| `schema_version` 在**文件头行**的 `_meta` 里，一个文件一个；无头的旧文件按 v0 读 | `elysper-session/src/jsonl.rs:104,117` | 版本号是文件级，不是行级；混版本文件在打开时就能发现 |
| v1 日志**本轮不迁移**；读端对旧版本**明确拒绝**（v0/v1 都拒），只有"比 2 新"才走另一条理由的同类错误 | 维护者已定："以后改格式有明确的兼容路径，而不是重开日志" + 拒绝旧版本 | 版本号的存在意义就在这显出来；代价是现存 v1 会话打不开、仓库 fixture 要重造 |
| 行的 `seq` 在**入队时**就分配并盖戳（`alloc_seq` → `stamp`），spill 里保留 `StampedRow { seq, value }` | `elysper-session/src/writer/mod.rs:302,459` | **A 不需要改格式**：重试认的就是那个已盖戳的 `seq`。只有 C 改行形状（assistant 行多一个 ledger key），所以只有 C 升版本 |
| `spawn_gates`（`state/app_state/mod.rs:135`）与 session controller（`session/controller/`）**同在 `elysper-server`** | 仓库现状 | **E 是本 crate 内的局部改动**，不跨 crate 边界，不动任何库 crate 的公开面 |
| "旧 park 行" = `SessionEvent::ParkedPrompt` 在 `park_id` 存在之前写的行（`park_id: String` 见 `events.rs:653`，消费方是 `ParkConsumed`，`events.rs:674`） | 仓库现状 | H 的范围确定：这些行只能按序号认，是"弃用 + 明说"还是"补一个升级过程" |
| `make test-crates` = 逐 crate 跑 `cargo test -p <crate> -q`（默认 feature，**含 doctest**），无 feature 矩阵 | `Makefile` | F 的判据明确；把它加进 `make ci` 是一行 |


## 6. 怎么落地

### 6.0 切分规则

**这条分支自己改过、或者只做了一半的，在这轮收尾；和 harness 无关的既有欠债也在这轮，
但单独成波、单独有门禁。**

用户已决定八项全部落在本分支。代价是 diff 跨 30+ crate 后不再能一眼看出核心改动；这一轮靠
"每项一个提交 + 每项一条验收行"来补偿 —— 验收记录按项列出，不按时间线。

### 6.1 波次与顺序

顺序的依据只有一条：**改持久化格式的先做**，因为后面所有验收都跑在新格式上。

```
第一波（改格式）   C 压缩写 durable 事件  →  A writer 不重复写行
        │                       同一批：elysper-session 的 writer + ledger
        ▼
第二波（语义，可并行） B awaiting_approval 不吞错
                        D stale_resume 拆成三个码
                        E gate 归 controller 所有
        ▼
第三波（收口）      G 文档说实话
                    H 边界规则去重 + 旧 park 行
        ▼
独立波（与 harness 无关，但本轮做） F 四个 crate 的测试变绿
```

**F 单独成波**不是因为它不重要 —— 它恰恰是"要成为社区基座"最难看的一类问题（社区克隆下来
`make test-crates` 就是红的）。是因为它和 harness 没有任何关系，混进重构 diff 里它反而最容易被
漏看。单独成波意味着它有自己的一条验收行。

### 6.2 八项的完成判据

每项都写"不变量"和"证据"两栏，缺一不算完。

| 项 | 不变量 | 证据 |
|---|---|---|
| **C** 压缩写 durable 事件 | 压缩后重放出的历史与实时看到的历史**逐行相同** | 同一份日志：实时 fold 出的 surface 与重放 fold 出的 surface 相等 |
| | 被替换的 assistant 行有 durable ledger key | `SurfaceLedger::resolve` 不再返回 `MissingKey` |
| | `CompactionRecord` 描述的区间 = 实际被替换的区间 | 记录里的 `start`/`end`/`source_indices` 与留下的行数一致 |
| **A** writer 不重复写行 | 一次 flush 失败后重试，日志里每一行只出现一次 | 注入 fsync 失败的后端，断言行数与 seq 连续性 |
| **B** 不吞读错误 | 读不到日志时，绝不把"读不到"当成"没有待审批" | 后端读失败 → 请求报错，且不启动新 run |
| **D** resume 三码 | 客户端能区分"已应用"/"别人推进了"/"没有快照" | 三个场景各断言一个不同状态码；前端跟着处理 |
| **E** gate 归 controller | 会话消失，gate 一起消失 | 跑过 N 个会话后，gate 表不增长（`Weak` 化） |
| **F** 四个 crate 绿 | `make test-crates` 退出 0 | 逐 crate 的失败用例先复现再修；`make ci` 之后新增它为门禁 |
| **G** 文档说实话 | 文档说的依赖数 = 实际 | fixture 的 `Cargo.toml` 与教程一致；`cargo tree` 的依赖数写进文档 |
| **H** 规则唯一 | 转场边界只有一处实现 | `routes/follow.rs` 不再自带一份；旧 park 行要么有升级过程，要么明说不支持 |

### 6.3 两条承诺

**公开 API 冻结（G3）。**
- 一份**承诺清单**：哪些 `pub` 名字是稳定的、承诺到哪个版本、改动它们要走过什么流程。
- 一条**门禁**：冻结 crate 的精选面里出现清单外的新公开名 → 失败，错误信息直接点名新增项。
- 门禁的落脚点是 `make check-pub-surface-strict` 的基线机制（它已经在逐 crate 记 `pub use` 计数），
  但**计数不够** —— 计数只挡数量不挡名字。名字要单独列。

**日志格式版本化（G2）。**
- `CURRENT_SCHEMA_VERSION` 从 1 升到 2 —— **只有 C 需要**：C 让 assistant 行带上 durable ledger key，
  这是行形状的变化。A 不升版本（重试认的是入队时就盖好的 `seq`，形状没变）。
- 读端**必须**按版本分支，规则是（**维护者已定：旧的明确拒绝，不尽力读**）：
  - 读到 **v2**（自己认识）：正常。
  - 读到 **v0（无头）/ v1**：**明确拒绝**，报一个专门的错误 —— 不是"打不开"，是
    "这份会话是用旧格式写的（v1），这一版不再读取它；请导出或重开会话"。
    拒绝的理由是：与其给你一个和当初不一样的上下文，不如明说这份日志的压缩历史不可恢复。
    静默降级才是真正危险的那个 —— 那会造出"看起来能用、其实不是"的历史。
  - 读到 **比 2 新**：同样拒绝（同一类错误，理由不同：写它的版本更新）。
- 版本号是**文件级**的（头行 `_meta.schema_version`），所以混版本文件在打开时就能发现，
  不会等到解析到一半。
- **后果（必须一并处理）**：
  - 仓库自己的 fixture 与测试要重造 —— 凡是写死 `schema_version: 1` 的都要改。
  - **这一轮之后，外部用户已有的 v1 会话会打不开**。这是维护者明确接受的代价，因为 crate 还在 0.1，
    而且"打开失败并说明原因"好过"打开成功但上下文不同"。
  - 错误必须**可操作**：文案里带上实际读到的版本、这一版支持的版本、以及下一步该做什么
    （导出 / 重开）。不能是一个泛化的 IO 错误。
  - **验收必须重跑**：分支此前的场景 A–I 是对着 v1 日志跑的，版本规则落地后要在 v2 上重跑一遍。

### 6.4 交接面（G4）

三份，都是给"不认识我们的人"看的：

1. **公开面清单**（人读）—— 与 §6.3 的承诺清单同源，但写成新用户视角：这个 crate 给你什么、
   哪些名字你该依赖。
2. **格式兼容说明**（人读）—— v1 与 v2 各是什么形状、碰到旧日志会怎样、为什么不做迁移。
3. **第一份材料**（人读）—— 从 clone 到跑通一条 turn，含零 tokio 那条路径。

## 7. 留给实现者的

- 八项各自的**实现方式**（哪几个文件、哪个 seam 用）。上面给的是不变量与证据，不是做法。
- 冻结清单的**具体名字**、承诺的**版本口径**、门禁脚本的**落点与失败信息格式**。
- 交接面三份的**篇幅与位置**（哪些进 crate README、哪些进 `docs/`、哪些进 `MINIMAL.md`）。
- F 四个 crate 的**根因修法**（`tokio::time` feature、过期 doctest 签名、doctest 参数个数与 feature
  各不相同；`elysper-resilience` 与 `elysper-tool-memo` 是同一个错，别的 crate 可能还有同类）。
- 验收记录**怎么补**：现有那份是"一次运行的机械记录"，本轮要变成"按项列出的收口记录"。

## 8. 明确的未知

- 冻结承诺覆盖到哪个版本号（0.2？1.0？）—— 影响清单的措辞，实现者可以先按"下一个 minor"写，
  由维护者定稿。
- 旧 park 行是升级还是弃用 —— 影响 H 的做法与 G4 第 2 份材料的措辞。实现者先按"弃用 + 明说"做，
  除非有更强理由。

## 9. 决策记录（这一轮的取舍，都由维护者定）

| 问题 | 决定 | 代价 |
|---|---|---|
| 八项遗留的范围 | **全部修**，且**都落在本分支** | diff 跨 30+ crate 后不再一眼看得出核心改动；靠"每项一个提交 + 每项一条验收行"补偿 |
| F（四个 crate 在 master 上就红） | 也在这轮做，但**单独成波、单独有门禁** | 它和 harness 无关，混进重构 diff 里最容易被漏看 |
| 这一轮的定位 | **交出去 + 补齐"基座"该有的承诺**（公开 API 冻结、格式版本化、交接面） | 冻结意味着以后想改公开面要先改承诺 |
| 日志格式向后迁移 | **不迁移**；版本号现在就埋，以后改格式有路 | 现存 v1 会话在本轮之后打不开（见 §6.3 的后果） |
| 公开 API 冻结锁到哪一层 | **只锁精选面**（harness 60 个名字）；深路径不承诺 | 用深路径的人没有预告 |
| 老日志（v0/v1）怎么读 | **明确拒绝**，报可操作的错误；不尽力读 | 现存会话立刻打不开，仓库 fixture 要重造，验收要重跑 |
