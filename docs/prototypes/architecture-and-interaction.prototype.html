插件树
核心树（Rust，进程内）永远存在；core 的 Fiber 状态机
UI 树 · 浏览器（JS）由 UI 装载器装；声明插槽
UI 树 · 终端（Rust）同一个 UI 装载器；终端也有一棵，所以 TUI 可扩展
插槽 id 与宿主无关：ui-bundle 行声明 chat.sidebar 之类， 浏览器渲染成 DOM、终端渲染成 ratatui ⇒ 新增一个 UI 插件，两个宿主同时拿到。
真源与可写层
  • 一行 = 一个插件的内容（DSH 同款）：插件 + 它的小配置
  • 大配置不进 profile：由插件自己管（自己的文件 / 自己的状态）
  • 插件按约定自己读排布：skill 插件读 skills/、mcp 插件读 mcp.json；profile 不复制这些数据
  • plugin 排布 = 读文件目录的手段与约定（识别能力数据），它不是"插件"
  • 插件 = cordis 插件 = 树里的单元（核心树的 Fiber / UI 树的 UI 插件）
  • profile = 最终产物（core 唯一认的组装入参）· 也是唯一可写的地方
  • 没有 settings：DSH 里 settings 是一个插件提供的服务，不是文件概念
  • 族 = 服务契约：tool 插件提供注册表服务，skill 插件 inject 它；树是平的（DSH：所有层摊平成一个列表，行序不决定装载序）
  • 启用位可由插件判定：行上的 enabled 除了真假，还能指向插件的判定 ⇒ 每个 skill 不必都写成 profile 行
  • skill 先是数据：skill 插件读 skills/ 自己判定启用并注册成工具；要变成插件时再显式加行
  • 内置 MCP = 改 profile 的通道（装得起来才生效）
  • 内置默认 agent = 整个 harness 的运转方式，不可停用
跨树硬边界
  • 核心装载器拒收 ui.* 服务键；UI 装载器拒收核心键
  • 违规在装配阶段失败，不是运行时串扰
  • core 不感知渲染目标：它只产出协议化事件流
本轮不动 / 要做
  • 不动：核心一行不动——kernel 语义、seam 链、profile 层序本身
  • 要做：UI 树（两个宿主）、profile 启用位、事务性变更、对话优先 IA
  • 要做：删掉旧 19 页（以新原型为准）

为什么能动态：组装入参是文件，运行时可改；改的是 profile，profile 就是那棵树的定义。
变更结果四态（对齐 DSH 的 application）：applied（已生效，刷新）· restart-required（要重启）· overridden（被更高层覆盖，未生效）· failed（装不起来 ⇒ 报错 ∧ 保持变更前）。界面与 MCP 都按这四态回报。

流 3 · 禁用语义

「能力与界面都是 profile 的行」的直接推论，也是这套模型的红利。
操作

界面开关 / MCP 都一样
→
装配
该行不挂载
不进 Fiber 树
→
能力
该工具 / agent / MCP 不可用
＋
界面
该界面区块不渲染
不是两套开关：一个开关同时管"能力在不在"和"界面在不在"，因为它们本来就是同一行。

为什么不进 profile：逐个 skill 的启用位会把 profile 撑成清单； 它属于 skill 插件自己的领域（DSH 的 settings 也是一个插件提供的服务）。
怎么判：行上的 enabled 可以指向插件的判定 （{ service, check, arg }）——对应 DSH 的 disabled: !!js … 表达式。
